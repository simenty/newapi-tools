    newapi-tools 安全基线（Security Baseline）

    版本：v0.1 适用范围：newapi-tools 项目全体模块（internal/、plugins/、CLI 命令等） 目标：提供一套最小但可执行的安全基线，用于指导日常开发、审计与发布。

    0. 基线设计原则

    • 最小可行：只包含「必须做到」的最低要求，而不是理想状态。
    • 可审计：每一条基线都能通过代码扫描、配置检查或测试来验证，而不是口头约定。
    • 可演进：随着 newapi-tools 的版本升级，可以按版本迭代本基线，并在审计报告中注明适用版本范围。

    1. 密钥与密码处理（Secrets Handling）

    1.1 存储与配置

    • 不得在源码中硬编码任何密钥、密码、AccessToken 等敏感信息。
    • 所有敏感配置必须来自：
    • 环境变量（如 NEWAPI_TOKEN、数据库密码）。
    • 外部配置文件（如 .env / INI / YAML），且该文件不纳入 Git 版本控制（通过 .gitignore 管理）。

    1.2 传递与使用

    • CLI 不得通过命令行参数（如 --password=xxx）传递敏感信息，避免通过进程列表被读取。
    • 推荐方式：
      • 使用环境变量（例如 MySQL 使用 MYSQL_PWD）。
      • 使用交互式输入（不回显）。
    • 在进程间传递敏感信息时，优先使用环境变量或管道，而非临时文件。

    1.3 脱敏与显示

    • 所有涉及密钥、Token、密码的字段在日志、错误信息、UI 输出中必须脱敏，仅允许部分显示：
    • 标准策略：显示前后 2 个字符，中间使用 * 替代（如 sk-AB***YZ）。
    • 对短于 6 个字符的敏感值，统一显示为 "*"。
    • 实现上必须按 rune（UTF-8 字符）切片，而非字节切片，避免中文/emoji 产生截断或 panic。

    2. 日志与审计（Logging & Audit）

    2.1 日志内容

    • 禁止在日志中记录以下信息的明文形式：
    • API Key / Token / 密码
    • 个人隐私数据（如手机号、邮箱，若后续引入）
    • 完整的请求/响应负载（尤其是可能包含敏感数据时）
    • 如需调试请求/响应，应：
    • 仅记录必要字段（如状态码、请求 ID、耗时）。
    • 对内容进行脱敏或截断（例如只记录前 100 字符并脱敏）。

    2.2 日志结构

    • 建议使用结构化日志（例如 Go 的 slog 或带字段的 logger），便于后续安全审计与分析。
    • 对关键安全事件使用明确的字段：
    • event: "auth_failed" | "config_perm_invalid" | "secret_masked" ...
    • actor: 用户/进程标识（如有）。
    • resource: 资源标识（如 config file 路径）。

    2.3 审计日志（未来扩展）

    • 对高风险操作（如：备份、恢复、自更新、变更配置）建议写入审计日志，至少包含：
    • 操作类型
    • 执行时间
    • 执行结果（成功/失败 + 原因码）
    • 审计日志同样不得记录敏感明文信息。

    3. 配置与文件权限（Config & File Permissions）

    3.1 配置文件

    • 所有包含敏感信息的配置文件必须拥有合理的权限限制：
    • 在类 Unix 系统中，0600 或 0640 是推荐权限。
    • internal/security 中的配置检查函数必须：
    • 检查配置文件权限是否过宽（如全局可读）。
    • 返回统一的结构化错误（通过 apperr），便于 doctor 命令分类处理。

    3.2 目录结构与缓存

    • 临时文件与缓存目录应：
    • 使用操作系统提供的临时目录（os.TempDir），避免写入敏感路径。
    • 定期清理，避免长期残留敏感数据。

    4. 错误处理与错误码（Error Handling）

    4.1 统一错误结构

    • 所有对外暴露的错误（CLI 输出、日志、doctor）必须通过 internal/apperr 统一构造：
    • 使用标准错误码（如 CodeConfigPerm, CodeSecretInvalid 等）。
    • 错误消息不包含敏感明文信息，只描述问题与位置。

    4.2 doctor 与诊断

    • doctor 命令应基于错误码而非字符串匹配，来判断：
    • 配置权限问题
    • 密钥/Token 缺失或格式错误
    • 日志配置不当等
    • 每新增一类安全检查，必须：
    • 在 doctor 中增加相应检查项。
    • 在本基线文档中增加对应条目。

    5. 自更新、备份与完整性（Self-update & Integrity）

    5.1 自更新

    • 自更新模块必须对下载的二进制/脚本做完整性校验（如 SHA256）。
    • 当校验失败时：
    • 终止更新流程
    • 保持现有版本可用
    • 在日志中记录事件（不包含敏感信息）

    5.2 备份与恢复

    • 备份文件应：
    • 包含校验信息（例如 checksum），以检测是否被篡改。
    • 存储在权限受控的目录中。
    • 恢复流程需要：
    • 验证备份文件完整性
    • 在失败时回滚到上一个已知安全状态

    6. 测试与 CI 要求（Testing & CI Requirements）

    6.1 单元测试覆盖

    • 以下模块中涉及安全逻辑的函数必须有单元测试覆盖：
    • internal/security（包括脱敏、权限检查等）
    • internal/selfupdate（网络异常、校验失败、文件替换失败等）
    • 其他处理密钥/密码/配置的模块
    • 单元测试应覆盖：
    • 正常路径
    • 常见异常路径（网络错误、权限不足、UTF-8 边界）
    • 极端 case（空字符串、超长字符串、多字节字符等）

    6.2 CI 基线

    • CI 必须至少包含：
    • go test ./...
    • 覆盖率门禁（例如 ≥ 60%，长期目标上调）。
    • 静态分析（如 golangci-lint），建议开启安全相关规则（如 gosec）并避免无差别关闭关键规则。

    7. 审计与基线演进（Audit & Evolution）

    • 每次进行全面审计时（例如：docs/audit-report-v3.5.md），需要：
    • 在报告中注明所依据的 security-baseline.md 版本。
    • 对每条基线进行打分：✅ 已满足 / ⚠️ 部分满足 / ❌ 未满足。
    • 新发现的安全问题：
    • 若具有普适性，应整理为新的基线条目并记录版本变更。
